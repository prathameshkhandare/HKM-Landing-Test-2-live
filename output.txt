DEVELOPER-ONLY TASKS
Vyasa Puja Guide page — hkmchennai.org
To hand to your web developer alongside the code bundle
The code bundle (app/blog/vyasa-puja-guide-offering/page.tsx, content.ts, and the two shared components) implements everything that can be fully specified in advance: metadata, JSON-LD, semantic markup, the FAQ, and image/analytics scaffolding. The items below need a real asset, a real credential, or a judgment call inside your live project, so they are left as clearly marked TODOs in the code for your developer to complete.
1. Source and upload real images
Hero image: a real, temple-approved photograph for the article header (path: /public/images/blog/vyasa-puja-offering-hero.jpg).
Social share (OG) image: 1200×630px, compressed, same subject (path: /public/images/blog/vyasa-puja-offering-og.jpg). This is what shows when the link is shared on WhatsApp, Instagram, X, etc.
Suggested subject: Srila Prabhupada with the Bay of Bengal seafront or the Dakshina Dwaraka Dham gopuram visible in the background, temple name overlay optional.
Why a developer, not Claude: Claude cannot generate a real photograph of Srila Prabhupada or the temple, and should not — these need to be genuine, temple-approved photography, not AI-generated images of a real religious figure. Someone with access to the temple's photo archive needs to select, crop, and compress the actual files.
2. Confirm Tailwind design tokens
The page uses brand-maroon, brand-navy, brand-gold, brand-cream, brand-teal, brand-terracotta and a serif font stack (Cormorant Garamond / Cinzel). The README.md in the bundle includes the exact tailwind.config.js snippet.
Check whether these tokens already exist in the live tailwind.config.js (they should, from the Yatramritam/Sri Lanka Yatra pages).
If they exist under different names, update the class names in page.tsx to match — don't create a second, conflicting token set.
Why a developer, not Claude: Only someone with the actual project repository can see what's already configured there.
3. Re-enable the submission button when the link is ready
The “Submit Your Offering” button has been deliberately left out of the current build — Section 11 only shows the explanatory text (watch temple communications for the submission window). The supporting code was not deleted, just disconnected, so re-enabling it is a small, contained change rather than a rebuild:
In page.tsx, restore the import: import TrackedSubmissionLink from "@/components/TrackedSubmissionLink"; and import { faqs, submissionUrl } from "./content";
In page.tsx, replace the HTML comment block just above the “12. Frequently Asked Questions” heading with the <TrackedSubmissionLink> button (kept in the bundle's README/previous version for reference), pointing href at submissionUrl.
Set the NEXT_PUBLIC_VYASA_PUJA_SUBMISSION_URL environment variable (or wire it to whatever CMS field already drives other yearly-changing fields on the site) once the current year's submission form/link is confirmed.
Make sure this can be updated without a full code redeploy each year, since the link and deadline change annually and are announced separately from this evergreen guide.
Why a developer, not Claude: Whether and when to show a submission button is a content/timing decision for the temple to make, and the exact form/link URL depends on whichever tool or CMS field the temple is actually using this year — neither is something Claude can decide or access on its own.
4. Analytics wiring
components/TrackedSubmissionLink.tsx assumes window.gtag is already available site-wide (loaded once in the root layout).
Confirm the site's existing GA4/gtag.js setup exposes window.gtag globally.
If the site uses Google Tag Manager only (no direct gtag.js), swap the tracking call for a dataLayer.push({ event: "vyasa_puja_offering_submit_click" }) instead — the code comment marks exactly where to change this.
Why a developer, not Claude: Only your developer can see which analytics loader is actually installed in the live root layout.
5. Sitemap, robots.txt & Search Console
If the site uses file-based/App Router routing with a dynamic sitemap (e.g. app/sitemap.ts or next-sitemap), confirm this new route is picked up automatically after deploy.
If the sitemap is manually maintained, add this URL with a <lastmod> date.
Confirm robots.txt does not disallow /blog/.
After deploy, submit/refresh the URL in Google Search Console and run it through the Rich Results Test to confirm the Article, FAQPage and BreadcrumbList schema all validate with no warnings.
Why a developer, not Claude: These require access to the live sitemap configuration, the deployed robots.txt, and a Google Search Console account connected to hkmchennai.org — none of which Claude can access.
6. Internal linking & navigation
Add this page to the blog index/listing page so it's discoverable through site navigation, not just direct link.
Once a related-posts data source exists, link to the other saint-glorification blogs (Bhaktivinoda Thakura, Madhavendra Puri, etc.) as noted in the code comment near the end of page.tsx.
Link “Vedabase” (Section 9) to vedabase.io and “Dakshina Dwaraka Dham” (intro) to the temple's About/Darshan page, if/when those exist as routes.
Why a developer, not Claude: These depend on the site's existing blog index and page structure, which Claude hasn't seen.
7. Dates and deploy-time constants
In page.tsx, set DATE_PUBLISHED and DATE_MODIFIED to the real ISO dates at time of first publish, and update DATE_MODIFIED only whenever the copy is next revised.
Why a developer, not Claude: These need to reflect the actual publish/edit history, which only your team knows.
8. Post-deploy QA
Run Lighthouse/PageSpeed Insights on the live URL and confirm LCP, CLS and INP are within Core Web Vitals thresholds; adjust font-loading strategy (e.g. next/font instead of a manual @font-face) if the serif fonts cause layout shift.
View-source the deployed page to confirm all body text, quotes and FAQ answers are present in the initial HTML (not injected client-side only).
Proofread the rendered Sanskrit diacritics (IAST characters like ā, ī, ṛ, ś) on the live site — some hosting/CDN pipelines or fonts can silently mangle these characters, so a visual check after deploy is worth doing.
Why a developer, not Claude: These all require the page actually running on your infrastructure — Claude has verified the component code compiles and renders correctly, but not how your specific hosting/CDN/font pipeline handles it.
